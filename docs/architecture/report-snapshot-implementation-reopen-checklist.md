# 报告快照实现重开回查步骤
时间：`2026-07-04`

## 一、文档定位

- `已确认`：本文档用于定义后续若出现真实触发条件时，应如何重新评估是否进入“报告快照存储实现”。
- `已确认`：本文档只整理回查步骤与入口，不新增生产代码、repository、schema、service 或 route。
- `已确认`：本文档是对 batch-64、batch-66 相关判断的统一回查入口，不替代原始边界文档。

## 二、为什么需要统一回查入口

当前阶段 6 已经有多份相关文档：

- 对象与模板边界
- 触发条件
- `snapshot_payload` 最小草案
- 实现门槛复核
- 首批 `report_type` 范围

如果后续真的出现导出、历史留痕或前端接入需求，直接重新从零判断，容易：

- 漏掉已有止步结论
- 重复讨论已经收口过的边界
- 从新需求直接滑进实现细节

因此，补一个统一回查步骤，可以让后续重新评估更稳定。

## 三、重开实现前的回查顺序

若后续再次讨论“是否进入报告快照存储实现”，建议按以下顺序回查：

### 第一步：确认是否真的出现触发条件

优先回看：

- `docs/architecture/report-snapshot-storage-trigger-conditions.md`

要确认的问题：

1. 是否出现历史留痕需求
2. 是否出现固定导出物需求
3. 是否出现同版复看需求
4. 是否出现围绕报告对象的真实页面或模板接入

判断规则：

- 若一级触发条件仍都不成立，则本轮不进入实现

### 第二步：确认当前止步结论是否需要被推翻

优先回看：

- `docs/architecture/report-snapshot-implementation-gate-review.md`

要确认的问题：

1. batch-66 中“不进入实现”的原因是否仍然成立
2. 当前是否已经补齐当时缺失的前提
3. 当前收益是否已经开始大于维护成本

判断规则：

- 若 batch-66 的止步原因大体仍成立，则继续保持暂缓

### 第三步：确认首批范围是否仍应保持极小

优先回看：

- `docs/architecture/report-snapshot-initial-report-type-scope.md`

要确认的问题：

1. 是否仍只从 `backtest_run_detail` 与 `batch_experiment_summary` 开始
2. 是否有人试图把 AI 报告、前端专用对象或导出专用类型一起带入

判断规则：

- 若没有特别强的新需求，仍应保持首批范围只含这两个类型

### 第四步：确认最小正文骨架是否足够

优先回看：

- `docs/architecture/report-snapshot-payload-minimal-draft.md`

要确认的问题：

1. `headline / key_stats / body / generated_from` 是否仍足够
2. 是否真的需要新增版本号、导出元数据、生成器版本等字段
3. 是否需要按 `report_type` 放宽 section 内容差异

判断规则：

- 若没有真实实现压力，不继续扩字段草案

### 第五步：再决定是否进入实现设计

只有前四步完成后，才进入如下问题：

1. 是否需要 repository
2. 是否需要落库 schema
3. 是否需要独立 report service
4. 是否需要生命周期管理

判断规则：

- 不允许跳过前四步，直接讨论实现细节

## 四、当前推荐的重开门槛

建议至少满足以下条件中的前两项之一，再进入实现设计复核：

- 明确历史留痕需求
- 明确固定导出物需求
- 明确同版复看需求
- 明确前端或模板真实接入需求

并且同时满足：

- 首批 `report_type` 范围可控
- `snapshot_payload` 骨架仍然清晰
- 新增维护成本已有合理收益支撑

## 五、当前明确不应触发重开的情况

以下情况仍不建议直接重开实现评估：

- 只是想把文档链路补得更完整
- 只是觉得未来可能会需要导出
- 只是想顺手把快照存储一起做了
- 只是想提前为前端做技术预留

这些情况更适合继续：

- 保持文档边界
- 等待真实需求
- 在需求出现后再走本回查步骤

- `已确认`：当前最合理的做法，是把“如何重新打开实现门”流程化，而不是现在直接进入实现。
- `基于当前上下文推断`：除非后续出现明确新需求，否则本回查文档应长期作为阶段 6 的统一重开入口。
