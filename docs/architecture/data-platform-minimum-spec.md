# 数据平台最小规格规划

## 一、文档定位

- `已确认` 本文档是数据平台的最小规格规划版，不是实现文档。
- `已确认` 本文档只定义第一阶段数据底座的能力边界、输入输出与分层关系。
- `已确认` 本文档不直接触发数据库设计、数据源接入或同步脚本编写。

- `docs/architecture/phase-1-stitching-plan.md`
- `docs/architecture/domain-boundary-spec.md`
- `docs/architecture/quant-platform-recomposition-plan.md`

## 三、范围边界

### 3.1 纳入范围

- `MarketDataRepository`
- 标的基础信息读取边界
- 日线行情读取边界
- 交易日历读取边界
- 本地缓存边界
- 数据同步边界
- provider 边界
- 查询输出边界
- 对 `backtest-kernel` 的输入边界
- 对后续 `factor-lab` 的读取边界

### 3.2 当前不纳入

- 外部数据源真实接入
- 数据库表结构设计
- 财务数据与指数成分的完整实现
- API 接口设计
- 定时任务与调度实现

## 四、模块目标

第一阶段数据平台只服务于以下目标：

1. 为新项目提供统一的市场数据读取入口
2. 支持最小的 `Stock / Bar / 交易日历` 数据访问
3. 以本地缓存为主，隔离外部数据源差异
4. 为回测内核提供稳定行情输入
5. 为后续因子计算提供稳定读取边界

## 五、总体设计原则

### 5.1 已确认

- 数据平台优先形成“统一读取入口 + 本地缓存 + provider 边界”三段式结构。
- 主承接优先参考 `SleeperCloudQuant-old` 的数据仓储与缓存思路。
- provider 分层方式优先参考 `TradingAgents-CN-main` 的结构思想，但不直接搬实现。
- 核心输入输出对象必须与 `domain-boundary-spec.md` 保持一致。

### 5.2 基于当前上下文推断

- 第一阶段优先解决“可读、可缓存、可供回测使用”，而不是“数据全覆盖”。
- 数据平台首阶段应默认服务于日线研究与回测场景，不追求高频或复杂实时场景。

## 六、最小数据流

### 6.1 数据读取阶段

- 接收标准化查询请求
- 识别查询对象类型：`Stock / Bar / 交易日历`
- 先从本地缓存层读取
- 若缓存缺失或不可用，再由 provider 层提供补充来源

### 6.2 数据标准化阶段

- 将读取结果转换为统一领域对象
- 屏蔽外部来源的字段差异
- 统一时间、标的标识和周期表达

### 6.3 数据输出阶段

- 向 `backtest-kernel` 输出标准化行情数据
- 向后续 `factor-lab` 输出可复用的读取边界
- 向上层查询调用者输出统一结果

## 七、核心能力规格

### 7.1 `MarketDataRepository`

#### 职责

- 作为统一市场数据访问入口
- 屏蔽缓存层、provider 层和上层调用方之间的差异
- 为回测、研究、报告和后续因子模块提供稳定读取契约

#### 最小输入

- 标的标识
- 时间范围
- 数据类型
- 周期或频率

#### 最小输出

- `Stock`
- `Bar`
- 交易日历条目或交易日集合

#### 语义来源

- `主参考` `SleeperCloudQuant-old`
- `补充参考` `TradingAgents-CN-main`

#### 待确认

- `MarketDataRepository` 是单一聚合入口，还是按对象类型拆分多个仓储接口
- 查询参数是否允许弱约束扩展字段

### 7.2 标的基础信息读取边界

#### 职责

- 提供最小静态标的信息读取能力
- 为行情、回测、因子和报告提供统一标的入口

#### 最小输入

- `symbol`
- `exchange`
- 标的筛选条件

#### 最小输出

- `Stock`

#### 边界要求

- 首阶段只保证最小静态身份信息可读
- 不在当前阶段扩展为全量公司资料中心

#### 待确认

- 行业分类是否属于首阶段强制字段
- 停牌、退市等状态字段的更新来源是否首阶段纳入

### 7.3 日线行情读取边界

#### 职责

- 提供回测与研究所需的最小日线行情读取能力

#### 最小输入

- `symbol`
- `exchange`
- `start_date`
- `end_date`
- `adjustment_mode`

#### 最小输出

- `Bar[]`

#### 边界要求

- 当前阶段只保证日线级别稳定读取
- 不要求分钟级或 tick 级真实可用

#### 待确认

- 复权模式是否在查询参数中显式体现
- 缺失行情的补齐策略是否在仓储层处理

### 7.4 交易日历读取边界

#### 职责

- 提供回测区间和研究区间的交易日校准能力

#### 最小输入

- 市场标识
- 时间范围

#### 最小输出

- 交易日集合

#### 边界要求

- 当前阶段只保证首个目标市场的交易日历稳定可读
- 不扩展为多市场复杂日历中心

#### 待确认

- 交易日历是否作为独立领域对象保留
- 是否需要提供“最近交易日”类辅助查询

### 7.5 本地缓存边界

#### 职责

- 作为数据平台首阶段主读取来源
- 降低上层对外部 provider 的直接依赖

#### 最小缓存范围

- 标的基础信息
- 日线行情
- 交易日历

#### 边界要求

- 缓存层对上暴露统一读取语义，不暴露底层存储细节
- 当前阶段不绑定具体数据库表结构到文档契约

#### 待确认

- 缓存失效策略是按时间窗还是按数据类型区分
- 缓存层是否保留数据来源标记

### 7.6 数据同步边界

#### 职责

- 负责把外部数据拉取到本地缓存
- 将同步行为与上层读取行为解耦

#### 最小同步范围

- 标的基础信息同步
- 日线行情同步
- 交易日历同步

#### 边界要求

- 当前阶段同步能力只作为后台准备能力，不作为实时查询的一部分
- 同步失败不应污染统一读取契约

#### 待确认

- 首阶段是否需要手动触发同步即可
- 是否需要显式区分首次全量同步与增量同步

### 7.7 provider 边界

#### 职责

- 抽象外部数据来源差异
- 为同步层或缓存回填层提供标准化输入

#### 最小输入

- 查询类型
- 标的范围
- 时间范围

#### 最小输出

- 原始但可转换的数据结果

#### 语义来源

- `结构参考` `TradingAgents-CN-main`
- `实现思路参考` `SleeperCloudQuant-old`

#### 边界要求

- provider 不直接对上暴露为业务主读取入口
- provider 只负责获取与初步转换，不承担领域契约定义

#### 待确认

- 首阶段是否只保留单 provider 抽象
- provider 是否需要能力探测或健康状态表达

### 7.8 查询输出边界

#### 职责

- 保证上层读取方拿到统一领域对象或统一对象集合
- 为不同消费方提供尽量一致的读取语义

#### 输出给 `backtest-kernel`

- 标准化 `Bar[]`
- 标的元信息
- 交易日集合

#### 输出给后续 `factor-lab`

- 标准化 `Bar[]`
- 标的基础信息
- 可扩展的数据读取入口

#### 边界要求

- 当前阶段不在数据平台层混入回测专用逻辑
- 查询输出对象不直接暴露 provider 原始字段

#### 待确认

- 是否需要为不同上游模块设计不同读取视图
- 是否需要在输出中保留数据质量标记

## 八、来源项目承接关系

### 8.1 承接 `SleeperCloudQuant-old`

- `MarketDataRepository` 主抽象
- 本地缓存与仓储边界思路
- 行情读取与交易日历读取思路
- 数据平台与回测层衔接思路

### 8.2 参考 `TradingAgents-CN-main`

- provider 分层组织方式
- 外部来源隔离方式
- 配置化管理思路

### 8.3 约束 `domain-boundary-spec.md`

- `Stock`
- `Bar`
- `Tick`

说明：

- 当前阶段只要求前两者稳定可用，`Tick` 仅保留语义预留

## 十二、发布判断

### 已验证项

- 第一阶段数据平台的最小边界已从读取、缓存、同步、provider、查询输出和上下游衔接六个方面收敛
- 主承接来源和结构参考来源已区分清楚

### 未验证项

- 本地缓存的最终存储形态
- 同步模式是手动优先还是增量优先
- 查询输出是否需要保留数据质量或来源元信息

### 阻塞原因

- 当前仍未进入字段级实现确认
- 外部数据来源授权与边界还需后续单独确认

### 潜在风险

- 若跳过统一仓储抽象直接让回测层读取 provider，后续会造成强耦合
- 若缓存边界与同步边界不清，后续数据一致性难以维护

### 发布判断

- `已确认` 本文档可作为进入数据平台实现前的最小规格基础
- `待确认` 仍不应把本文件直接视为最终实现契约
