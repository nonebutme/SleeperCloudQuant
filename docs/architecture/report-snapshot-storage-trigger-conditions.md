# 报告快照存储触发条件
时间：`2026-07-04`

## 一、文档定位

- `已确认`：本文档用于定义 `阶段 6：报告存储与模板边界` 中，什么情况下才值得把“报告快照”从文档边界推进到真实存储实现。
- `已确认`：本文档只定义触发条件与止步条件，不新增 repository、schema、service 或 route。
- `已确认`：本文档以 `docs/architecture/report-object-and-template-boundaries.md` 为前置边界。

## 二、为什么需要触发条件

当前已经明确：

- `阶段 5：报告层（reporting）` 的读取面已冻结
- `阶段 6` 先做对象边界与模板边界澄清
- “报告快照层”目前仍处于文档定义阶段

因此，下一步不应因为“可以做存储”就直接做存储，而应先确认是否已经出现足够明确的真实需求。

## 三、建议的一级触发条件

只有出现以下任一情况，才建议认真进入“报告快照真实存储”设计：

### 3.1 需要历史留痕

表现为：

- 同一个 `run_id` 或 `experiment_id` 的查看结果可能随底层数据演化而变化
- 业务上希望保留“当时生成出来的那一版报告”
- 后续需要做前后版本比较

判断：

- `已确认`：这是最强的快照存储触发条件之一

### 3.2 需要固定导出物

表现为：

- 需要导出 Markdown、HTML、PDF 或其他静态结果
- 导出结果要求可复查、可复用、可重复查看
- 导出内容不能依赖未来再次实时拼装

判断：

- `已确认`：只要导出物需要“稳定复现”，就更适合基于快照而不是临时读取对象

### 3.3 需要多次复看同一版报告

表现为：

- 用户会多次打开同一份报告
- 希望不同时间点看到的是同一版结果
- 不希望每次查看都重新受当前数据库状态影响

判断：

- `已确认`：如果“同一份报告”已经被当成独立对象使用，快照存储的合理性会明显上升

### 3.4 需要与模板或前端真实接入

表现为：

- 前端开始围绕某一份“报告”做页面结构、导出按钮、历史列表或详情页
- 模板层需要绑定到稳定的报告正文载荷
- 页面不再只是直接消费 run detail / batch summary 的读取接口

判断：

- `已确认`：当页面围绕“报告对象”而不是“读取对象”展开时，通常已经接近需要快照存储

## 四、建议的二级触发条件

以下条件单独出现时，不一定足够，但若与一级条件叠加，则更适合推进存储实现：

### 4.1 需要版本比较

例如：

- 同一策略不同时间生成的报告要比较
- 同一 batch 的不同导出版本要比较

### 4.2 需要审计或复盘

例如：

- 想追溯当时导出的报告内容
- 想确认报告中的某项结论来自哪次生成

### 4.3 需要异步生成报告

例如：

- 报告生成与报告查看不再是同一步
- 先生成，后读取，期间存在等待、失败重试或队列处理

### 4.4 需要独立报告列表

例如：

- 不再只是“从 run/batch 进入报告”
- 而是出现“报告中心”“报告历史”“最近导出报告”等入口

## 五、当前明确不足以触发存储实现的情况

以下情况目前不建议单独作为引入快照存储的理由：

- 只是想把文档定义得更完整
- 只是觉得未来也许会有导出需求
- 只是想为可能存在的前端做提前设计
- 只是当前 route 返回字段还不够顺手

这些情况更适合继续通过：

- 文档澄清
- 读取对象整理
- 模板边界说明

来处理，而不是直接进入持久化实现。

## 六、当前建议的止步规则

在出现明确触发条件前，建议继续保持：

- 不新增报告快照 repository
- 不新增报告快照落库结构
- 不新增独立报告 service
- 不新增报告列表类 endpoint

原因：

- 当前 reporting 读取面刚完成冻结
- 快照对象边界刚完成文档定义
- 现在直接进入存储实现，容易把“可选能力”提前做成“必须维护的系统层”

## 七、推荐的最小判断顺序

当后续再次评估是否需要快照存储时，建议依次问四个问题：

1. 是否需要保留某一时刻的固定报告版本
2. 是否需要导出或复看这份固定版本
3. 是否已经出现面向“报告对象”的页面或模板接入
4. 是否已经值得为此引入 repository / schema / lifecycle

只有前两问至少有一个明确成立，且后三问开始出现真实落地压力时，才建议继续推进实现。

## 八、阶段判断

- `已确认`：当前最合适的做法，是先把“何时值得做快照存储”讲清，而不是直接实现。
- `基于当前上下文推断`：下一步若继续推进，最小动作应是补充“报告快照最小字段草案”，而不是马上开始存储建模。
