# 配置中心最小规格规划

## 一、文档定位

- `已确认` 本文档是配置中心的最小规格规划版，不是实现文档。
- `已确认` 本文档只定义第一阶段最小配置能力的边界、分类和依赖关系。
- `已确认` 本文档不直接触发配置加载代码、密钥管理或 UI 管理页面开发。

## 二、输入来源

- `docs/architecture/phase-1-stitching-plan.md`
- `docs/code-archaeology/candidate-capability-routing.md`
- `docs/architecture/quant-platform-recomposition-plan.md`
- `docs/architecture/data-platform-minimum-spec.md`
- `docs/architecture/backtest-kernel-minimum-spec.md`

## 三、范围边界

### 3.1 纳入范围

- 数据源配置边界
- 回测默认参数配置边界
- 报告模板配置边界
- 模型配置边界
- 配置读取与校验边界
- 配置启用状态边界

### 3.2 当前不纳入

- 环境变量落地方案
- 密钥管理实现
- 配置文件格式实现
- UI 管理页面
- 多环境配置发布流程

## 四、模块目标

第一阶段配置中心只服务于以下目标：

1. 为 `data-platform` 提供最小数据源配置能力
2. 为 `backtest-kernel` 提供最小默认参数配置能力
3. 为后续 `ai` 和 `reporting` 预留最小模型与模板配置边界
4. 让关键能力在不改代码的前提下具备可调整性

## 五、总体设计原则

### 5.1 已确认

- 配置中心优先服务于系统底座，而不是先服务于管理界面。
- 主参考优先采用 `TradingAgents-CN-main` 的配置分类与组织思路。
- 配置对象不应直接绑定某个具体加载实现。
- 配置边界必须与 `data-platform`、`backtest-kernel`、`reporting` 的最小规格保持解耦。

### 5.2 基于当前上下文推断

- 第一阶段更适合“少量高价值配置”，不适合一次性引入完整配置系统。
- 配置中心首阶段应优先保证分类清晰，而不是追求细粒度灵活性。

## 六、配置分类

### 6.1 数据源配置

#### 职责

- 控制首阶段外部数据来源的启用状态和基本读取参数。
- 为 `data-platform` 的 provider 与同步边界提供最小配置支持。

#### 最小字段范围

- `source_id`
- `source_name`
- `enabled`
- `priority`
- `market_scope`
- `capabilities`

#### 依赖模块

- `data-platform`

#### 承接来源

- `主参考` `TradingAgents-CN-main`
- `补充参考` `SleeperCloudQuant-old`

#### 待确认

- 是否需要把认证信息与功能配置分离
- `priority` 是否首阶段必须保留

### 6.2 回测默认参数配置

#### 职责

- 为 `backtest-kernel` 提供默认执行参数。
- 避免每次回测都重复声明基础参数。

#### 最小字段范围

- `default_benchmark`
- `default_initial_cash`
- `default_frequency`
- `default_slippage`
- `default_commission`
- `default_market`

#### 依赖模块

- `backtest-kernel`

#### 承接来源

- `主参考` `TradingAgents-CN-main`
- `补充参考` `SleeperCloudQuant-old`

#### 待确认

- `slippage` 和 `commission` 是否首阶段只允许全局默认值
- 是否需要按市场或策略类型区分默认参数

### 6.3 模型配置

#### 职责

- 为后续 `ai` 与部分报告生成场景预留最小模型配置边界。
- 控制模型可用性，而不是在当前阶段展开完整模型平台能力。

#### 最小字段范围

- `model_id`
- `provider`
- `enabled`
- `model_name`
- `purpose`
- `timeout`

#### 依赖模块

- 后续 `ai`
- 可能的 `reporting`

#### 承接来源

- `主参考` `TradingAgents-CN-main`

#### 待确认

- 首阶段是否真的需要在配置中心保留模型配置
- `purpose` 是否需要区分分析、总结、报告等用途

### 6.4 报告模板配置

#### 职责

- 为 `reporting` 提供最小模板分类与启用边界。
- 让报告结构具备基础可变性。

#### 最小字段范围

- `template_id`
- `template_name`
- `report_type`
- `enabled`
- `version`
- `summary_schema_ref`

#### 依赖模块

- `reporting`

#### 承接来源

- `基于当前上下文推断` 以新项目自定义为主
- `补充参考` `TradingAgents-CN-main`

#### 待确认

- 首阶段是否只保留回测报告模板
- `summary_schema_ref` 是文本模板引用还是结构定义引用

## 七、配置读取与校验边界

### 7.1 读取边界

#### 职责

- 为上层模块提供统一配置读取入口
- 屏蔽配置来源的内部差异

#### 边界要求

- 当前阶段只要求“可读取”和“可区分启用状态”
- 不要求支持复杂热更新或动态变更广播

#### 待确认

- 读取入口是单一配置服务还是分类读取服务
- 是否需要配置快照概念

### 7.2 校验边界

#### 职责

- 在配置被使用前做最小结构与状态校验
- 避免非法配置直接进入业务模块

#### 最小校验范围

- 必填字段存在
- 启用状态合法
- 基础类型合法
- 关键引用不为空

#### 边界要求

- 当前阶段只做最小静态校验
- 不引入复杂规则引擎

#### 待确认

- 是否需要区分“配置缺失”和“配置存在但无效”
- 校验失败返回摘要还是结构化错误对象

## 八、配置启用状态边界

### 8.1 职责

- 表达某项配置是否可被当前系统能力使用
- 支撑首阶段最小开关控制

### 8.2 最小状态范围

- `enabled`
- `disabled`

### 8.3 边界要求

- 当前阶段不引入更复杂的灰度、分组、环境级开关系统
- 启用状态只服务于最小功能控制

### 8.4 待确认

- 是否需要补充 `deprecated` 状态
- 是否需要记录启用状态变更原因

## 九、与其他模块的依赖关系

### 9.1 对 `data-platform`

- 提供数据源启用状态
- 提供 provider 优先级和功能范围

### 9.2 对 `backtest-kernel`

- 提供默认市场、基准、资金、频率和成本参数

### 9.3 对 `reporting`

- 提供模板分类与启用边界

### 9.4 对后续 `ai`

- 提供最小模型可用性边界

## 十四、发布判断

### 已验证项

- 第一阶段配置中心的最小边界已从数据源、回测参数、模型、报告模板、读取校验、启用状态六个方面收敛
- 主参考来源与补充来源已区分清楚

### 未验证项

- 模型配置是否首阶段必须保留
- 报告模板配置是否只保留回测报告
- 数据源配置与认证信息是否拆层

### 阻塞原因

- 当前仍未进入字段级实现确认
- 配置持久化和加载机制仍需后续单独规格化

### 潜在风险

- 若配置分类过多，首阶段会偏离底座优先目标
- 若数据源、回测、模型配置混在一起实现，后续维护成本会变高

### 发布判断

- `已确认` 本文档可作为进入配置中心实现前的最小规格基础
- `待确认` 仍不应把本文件直接视为最终实现契约
