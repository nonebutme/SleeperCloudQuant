# 阶段 7 目标与边界定义
时间：`2026-07-05`

## 一、文档定位

- `已确认`：本文档用于定义 `SleeperCloudQuant` 在阶段 6 之后，下一阶段真实开发的目标、边界与非目标。
- `已确认`：本文档不重开阶段 5 `reporting` 冻结边界，也不直接触发阶段 6 报告快照存储实现。
- `已确认`：本文档的作用，是把后续开发主线从“继续补边界文档”切换为“收束最小应用闭环”。

## 二、为什么需要阶段 7

截至当前上下文：

- 阶段 5 `reporting` 已形成冻结基线
- 阶段 6 已形成报告对象、快照触发条件、最小载荷和重开回查入口
- `domain`、`app/services`、`app/api`、`app/main.py` 已出现正式模块骨架

此时如果继续：

- 回到阶段 5 补 `reporting` 字段或 route
- 直接进入阶段 6 快照存储实现
- 直接切到前端页面或 AI 全链路

都容易与当前已经收口的阶段判断冲突。

因此，阶段 7 更合理的定位，是把现有正式模块收束成一个可被稳定调用、可被最小验证覆盖的本地量化服务闭环。

## 三、阶段 7 目标

阶段 7 的目标是：

- 把当前已有的正式模块推进为最小可调用应用骨架
- 形成“数据查询 -> 单次回测 -> 结果读取”的最小本地服务闭环
- 让验证入口从“模块可导入”进一步提升为“服务与 API 可稳定回归”

更具体地说，阶段 7 应优先收束以下三个结果：

1. 数据查询链可被应用服务和 API 稳定调用
2. 单次回测链可返回最小结果摘要并被读取
3. 报告读取链继续沿用阶段 5 冻结基线，在不扩边界的前提下纳入最小回归

## 四、阶段 7 边界

阶段 7 允许进入的工作范围，仅限以下几类：

### 4.1 领域与服务编排收束

- 收束 `domain` 中已存在的最小对象语义
- 对齐 `app/services` 中数据、回测、报告相关服务的最小职责
- 修正当前实现与文档计划之间的滞后描述

### 4.2 最小 API 访问面收束

- 收束 `app/api` 与 `app/main.py` 中的最小访问入口
- 保持接口面聚焦于：
  - 市场数据读取
  - 单次回测提交
  - 回测结果读取
  - 既有 reporting 只读查询

### 4.3 服务级验证收束

- 补齐或整理服务层 smoke 验证
- 补齐或整理 API 层 smoke 验证
- 让验证基线文档与当前真实命令集一致

## 五、阶段 7 非目标

阶段 7 明确不做以下事项：

- 不继续扩阶段 5 `reporting` 字段与只读 endpoint
- 不直接进入阶段 6 报告快照 `repository / schema / service / route` 实现
- 不做前端页面实现
- 不做 AI 分析流程接入
- 不做异步任务系统
- 不做多用户权限
- 不做实盘交易
- 不做跨市场全量扩展
- 不补齐完整交易对象全集或事件总线体系
