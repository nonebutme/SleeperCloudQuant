# web-app 首批实现批次范围（按页面优先顺序）
时间：`2026-07-06`

## 一、文档定位

- `已确认`：本文档用于定义 `SleeperCloudQuant` 在 `web-app` 最小访问层下，首批实现批次的任务范围与页面推进顺序。
- `已确认`：本文档只定义实现批次范围，不直接开始前端编码。
- `已确认`：本文档默认沿用用户已确认的页面顺序：`页面 A -> 页面 D -> 页面 C -> 页面 B`。

## 二、为什么需要实现批次范围

当前已经完成：

- `web-app` 最小访问层目标、边界与非目标定义
- 首批页面清单与页面级非目标定义

如果此时直接进入实现，而不继续收束批次范围，后续很容易出现：

- 一次性并行做四页
- 页面壳层、联调、视觉细节同时展开
- 又把后端扩面、AI、导出、配置中心等需求混入首批实现

因此，需要先把“首批实现到底先做哪些、做到什么程度、哪些先不做”写清楚。

## 三、首批实现顺序

用户已确认的页面实现顺序为：

1. 页面 A：市场数据查询页
2. 页面 D：reporting 只读结果页
3. 页面 C：单次回测提交与结果查看页
4. 页面 B：因子查询页

该顺序的含义是：

- 先做最直观、最容易感知的读取面
- 再做结果查看页，确认 reporting 只读对象的可见性
- 然后再进入单次回测提交
- 最后再接入相对更厚的因子查询面

## 四、首批实现批次建议拆分

### 4.1 批次 1：页面 A 静态壳层 + 最小联调入口

目标：

- 建立 `web-app` 最小页面壳层与导航框架
- 完成页面 A 的最小表单、最小结果区与最小错误提示区
- 打通 `market` 读取类接口的首条页面访问路径

本批只做：

- 页面壳层
- 页面 A
- 最小导航
- 最小请求与结果展示

本批不做：

- 页面 D / C / B
- 复杂图表
- 批量查询
- 页面联动逻辑

### 4.2 批次 2：页面 D 最小只读结果查看

目标：

- 打通 run detail 与 batch summary 的最小只读查看路径
- 验证 reporting 冻结基线在页面层是否足够可读

本批只做：

- 页面 D
- run detail 查看
- batch summary 查看
- 与页面 A 共享的最小导航壳层复用

本批不做：

- reporting 列表
- 搜索过滤
- 导出中心
- 历史版本浏览

### 4.3 批次 3：页面 C 单次回测提交与结果跳转

目标：

- 打通单次回测提交
- 提交成功后跳转到对应 run detail
- 验证“提交 -> 查看结果”的页面路径是否成立

本批只做：

- 页面 C
- 最小回测表单
- 最小成功/失败提示
- 跳转到页面 D 的最小链路

本批不做：

- 批量实验工作台
- 异步任务中心
- 策略编辑器
- 扩展回测参数面板体系

### 4.4 批次 4：页面 B 因子查询页

目标：

- 在前面三批已经形成页面壳层与最小联调习惯后，再接入较厚的因子查询面
- 验证因子只读与研究查询面在页面层的最小可用性

本批只做：

- 因子定义读取
- 股票池成员读取
- 摘要 / values / top-n 的最小查询展示

本批不做：

- 因子编辑器
- 导出中心
- 因子计算任务入口
- 复杂研究工作流界面

## 五、首批实现共通约束

所有实现批次都应同时遵守以下约束：

- 不扩后端 route 数量
- 不重开阶段 5 `reporting` 字段面
- 不进入阶段 6 报告快照实现
- 不引入 AI 页面
- 不引入配置中心页面
- 不引入登录、权限、租户或会话流程
- 不为了样式表现而先扩大交互复杂度

## 六、首批实现完成判断

若后续进入实现，首批实现更适合以以下标准判断是否达标：

1. 页面 A 已能稳定查询并展示最小市场数据结果
2. 页面 D 已能稳定展示 run detail 与 batch summary
3. 页面 C 已能完成单次回测提交并跳转查看结果
4. 页面 B 已能在不扩后端能力面的前提下完成最小因子查询
5. 整个过程没有把首批 `web-app` 实现重新做成大而全平台壳子

## 七、当前建议结论

- `建议`：若下一步进入 `web-app` 实现，应严格按 `A -> D -> C -> B` 的批次顺序推进。
- `建议`：真正开始写前端代码前，可再补一份“批次 1 具体任务清单”，只围绕页面 A 与最小壳层展开。
- `已确认`：在本文档基础上，后续已经可以进入 `web-app` 首批实现批次定义或直接进入批次 1 实现准备。
