## 四、候选主线

### 4.1 候选主线 A：`web-app` 最小访问层

适用触发条件：

- 明确需要 PC 端 Web 界面
- 需要把当前已有服务与 API 闭环变成可直接使用的页面入口
- 需要验证“后端最小闭环”是否足以支撑真实产品访问路径

建议目标：

- 只做最小 PC Web 访问面
- 先以读取、浏览、触发既有接口为主
- 不在首批阶段引入复杂状态管理、权限系统或页面专用后端扩面

首批边界建议：

- 市场数据查询页面
- 因子查询页面
- 单次回测提交与结果读取页面
- 既有 reporting 只读结果查看页面

明确非目标：

- 不做完整产品化后台
- 不做多用户权限
- 不做大规模前端组件体系重建
- 不倒逼后端重开阶段 5 或阶段 6

### 4.2 候选主线 B：报告快照实现重开评估

适用触发条件：

- 明确出现导出需求
- 明确出现历史留痕需求
- 明确出现同版复看需求
- 明确出现前端模板或固定展示对象接入需求

建议目标：

- 不直接进入实现
- 先按 `report-snapshot-implementation-reopen-checklist.md` 做统一回查
- 只有在触发条件成立后，才进入实现设计

首批边界建议：

- 只讨论是否重开实现门
- 不提前新增 `repository / schema / service / route`
- 若真进入实现，首批 `report_type` 仍应极小

明确非目标：

- 不因为“以后可能会用到”就提前做
- 不把快照存储当成前端预埋工程
- 不顺手扩 AI 报告类型或导出专用类型

### 4.3 候选主线 C：`ai` 最小分析链路

适用触发条件：

- 明确出现单股 AI 分析需求
- 明确出现结构化 AI 研究报告需求
- 明确需要把本地量化数据与模型调用接起来形成首条 AI 产品链路

建议目标：

- 只做与量化研究平台强相关的最小 AI 链路
- 从单股分析或单次任务入口开始
- 保持 AI 输出范围可控、可验证、可追溯

首批边界建议：

- 单任务入口
- 结构化输出骨架
- 最小模型配置读取
- 最小运行日志或错误状态透出

明确非目标：

- 不做多智能体产品化全量能力
- 不做复杂工作流编排平台
- 不在首批阶段直接扩前端全页面协作体验

### 4.4 候选主线 D：`config-center` 实用化补强

适用触发条件：

- 当前本地运行已经出现明显配置管理痛点
- 数据源、模型或默认回测参数需要更稳定的显式配置入口
- 后续 Web 或 AI 主线继续推进前，配置层已成为真实阻塞

建议目标：

- 先补最小可维护配置面
- 为后续 Web 或 AI 主线提供稳定配置入口
- 不扩大为完整运维平台或多环境部署体系

明确非目标：

- 不做大规模配置平台化改造
- 不引入与当前本地化项目阶段不相称的复杂环境体系
