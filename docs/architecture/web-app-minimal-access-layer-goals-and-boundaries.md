# web-app 最小访问层目标与边界定义
时间：`2026-07-05`

## 一、文档定位

- `已确认`：本文档用于定义 `SleeperCloudQuant` 在阶段 7 之后，若选择 `web-app` 作为下一阶段主线时的目标、边界与非目标。
- `已确认`：本文档只定义最小访问层，不直接触发前端实现。
- `已确认`：本文档以当前阶段 7 已形成的最小服务与 API 闭环为承接底座，不重开阶段 5 `reporting` 冻结边界，也不直接触发阶段 6 报告快照实现。

## 二、为什么下一阶段优先定义 `web-app`

基于当前上下文：

- `已确认`：项目总目标已明确指向“PC 端 Web 量化分析平台”。
- `已确认`：阶段 7 已经完成 `app/services + app/api + http_adapter + unified formal verification` 的最小闭环收束。
- `已确认`：当前继续停留在后端内部微调的边际收益已经下降。

因此，若没有更强的新需求牵引，最自然的下一步不是继续补后端细节，而是验证当前最小闭环能否承接一个最小可访问的 Web 产品入口。

## 三、web-app 最小访问层目标

若选择 `web-app` 作为下一阶段主线，首要目标应是：

- 把当前已有后端最小闭环转化为可访问的 PC Web 界面入口
- 验证当前 API 与服务层是否足以支撑最小产品访问路径
- 在不扩大后端能力面的前提下，形成“查询 -> 提交 -> 查看结果”的首条页面链路

更具体地说，`web-app` 最小访问层应优先收束以下结果：

1. 用户可通过页面访问市场数据与因子查询能力
2. 用户可通过页面提交单次回测并读取结果
3. 用户可通过页面查看既有 reporting 只读结果
4. 页面层不倒逼后端扩新 route、新字段或快照存储实现

## 四、首批范围边界

`web-app` 最小访问层首批允许进入的范围，仅限以下几类：

### 4.1 页面入口范围

首批页面建议只保留以下四类：

- 市场数据查询页
- 因子查询页
- 单次回测提交与结果查看页
- reporting 只读结果查看页

### 4.2 交互范围

首批交互只允许：

- 查询
- 表单提交
- 结果展示
- 最小错误提示
- 最小导航切换

当前不要求进入：

- 拖拽式研究流
- 复杂筛选面板体系
- 多步骤任务编排体验
- 报告编辑器或导出工作台

### 4.3 后端承接边界

首批 `web-app` 应直接复用现有阶段 7 闭环：

- `market` 读取接口
- `factors` 查询接口
- `backtest` 最小执行接口
- `reporting` 只读接口
- `http_adapter` 或现有 API shell

原则上：

- 不为了页面方便而先扩 route
- 不为了页面展示而先重开阶段 5 `reporting` 字段面
- 不为了结果留痕而先进入阶段 6 快照实现

## 五、首批非目标

`web-app` 最小访问层明确不做以下事项：

- 不做完整产品后台或全量工作台
- 不做多用户、权限、租户或登录体系
- 不做复杂前端状态管理平台化建设
- 不做页面专用聚合接口扩张
- 不做 AI 分析流程接入
- 不做报告快照、导出中心或历史版本浏览体系
- 不做移动端适配

## 六、首批成功标准

若进入 `web-app` 最小访问层，首批更适合以以下标准判断是否完成：

1. 页面能稳定调用当前阶段 7 已有后端入口
2. 最小查询与回测提交流程能走通
3. reporting 只读结果能在页面被查看
4. 未引入新的后端扩面冲动或阶段越界实现
5. 能为后续是否继续扩 Web 层提供真实使用反馈

## 七、与其他候选主线的关系

### 7.1 与报告快照主线的关系

- `已确认`：`web-app` 最小访问层不是报告快照实现的替代入口。
- `已确认`：若页面随后出现固定导出、历史留痕或同版复看需求，应单独触发报告快照重开评估，而不是在 `web-app` 首批阶段顺手补做。

### 7.2 与 AI 主线的关系

- `已确认`：`web-app` 最小访问层当前只承接既有量化服务闭环，不承接 AI 分析流程。
- `建议`：若未来出现 AI 页面入口需求，应先单独定义 AI 最小分析链路，再决定如何映射到 Web 页面。

### 7.3 与 config-center 主线的关系

- `基于当前上下文推断`：若进入 `web-app` 后发现配置入口成为真实阻塞，再单独评估是否补 `config-center` 最小可维护配置面。
- `已确认`：当前不应在 `web-app` 首批阶段顺手打开更重的配置平台化工作。

## 八、阶段判断

- `建议`：下一阶段若继续推进，默认可将 `web-app` 最小访问层作为唯一主线。
- `建议`：在 `web-app` 首批阶段，应先做“访问面验证”，而不是追求完整产品化体验。
- `已确认`：只有在本文件目标、边界与非目标明确后，才适合创建对应的新阶段执行批次并进入实现。
