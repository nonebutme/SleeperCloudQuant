# 跨文档一致性检查计划

## 一、文档定位

- `已确认` 本文档用于检查当前项目主干规划文档之间的一致性。
- `已确认` 本文档只定义检查目标、检查清单、冲突判定规则和处理优先级。
- `已确认` 本文档不直接修改任何现有规划文档。

## 二、检查范围

本轮检查只覆盖以下 5 份主干文档：

- `docs/architecture/phase-1-stitching-plan.md`
- `docs/architecture/domain-boundary-spec.md`
- `docs/architecture/backtest-kernel-minimum-spec.md`
- `docs/architecture/data-platform-minimum-spec.md`
- `docs/architecture/config-center-minimum-spec.md`

## 三、检查目标

本轮检查只回答以下问题：

1. 术语是否前后一致
2. 对象命名是否前后一致
3. 模块职责是否存在重叠或冲突
4. 上下游依赖是否互相打架
5. “已确认 / 待确认 / 当前不纳入” 是否表述矛盾
6. 来源仓库承接关系是否前后一致

## 四、检查维度

### 4.1 术语一致性

检查内容：

- `data-platform`
- `backtest-kernel`
- `config-center`
- `reporting`
- `domain`
- `provider`
- `cache`
- `gateway`
- `result`
- `request`

检查目标：

- 同一术语在不同文档中不出现职责漂移
- 中英文表达不混乱
- 同一概念不被多个近义词反复替换

判定规则：

- 若同一术语在不同文档中表达的是同一职责，则判为 `一致`
- 若同一术语在不同文档中承担不同职责，则判为 `冲突`
- 若两个不同术语实为同一概念但未显式说明，则判为 `待统一`

### 4.2 对象命名一致性

检查内容：

- `Stock`
- `Bar`
- `Tick`
- `Order`
- `Trade`
- `Position`
- `Account`
- `BacktestRequest`
- `BacktestResult`
- `AnalysisReport`
- `BacktestReport`
- `FactorDefinition`
- `FactorValue`
- `StrategyDefinition`

检查目标：

- 对象名称在不同文档中引用一致
- 对象在不同模块中的输入输出角色不冲突

判定规则：

- 若对象名称与主要用途一致，则判为 `一致`
- 若对象在不同文档中承担互斥角色，则判为 `冲突`
- 若对象存在但上下游引用不完整，则判为 `待补齐`

### 4.3 模块职责一致性

检查内容：

- `data-platform`
- `backtest-kernel`
- `config-center`
- `reporting`

检查目标：

- 每个模块职责边界清晰
- 不出现同一职责被两个模块重复承载
- 不出现上层职责下沉到底层模块

判定规则：

- 若职责只在一个主模块中出现，其他文档仅引用，则判为 `一致`
- 若两个模块都把同一职责定义为本模块核心职责，则判为 `冲突`
- 若职责未明确归属，则判为 `待确认`

### 4.4 依赖关系一致性

检查内容：

- `data-platform -> backtest-kernel`
- `data-platform -> factor-lab`
- `backtest-kernel -> reporting`
- `config-center -> data-platform`
- `config-center -> backtest-kernel`
- `config-center -> reporting`

检查目标：

- 上下游依赖方向一致
- 不出现循环依赖暗示
- 不出现被依赖模块反向要求暴露实现细节

判定规则：

- 若依赖方向单向明确，则判为 `一致`
- 若上下文暗示相互依赖或职责回流，则判为 `冲突`
- 若依赖存在但接口边界未描述，则判为 `待细化`

### 4.5 范围边界一致性

检查内容：

- `已确认`
- `待确认`
- `当前不纳入`
- `当前不做`

检查目标：

- 某项能力在一份文档中被排除后，不应在另一份文档中被默认纳入
- 某项结论若仍为 `待确认`，不应在其他文档中被写成既定事实

判定规则：

- 若状态表述在各文档中一致，则判为 `一致`
- 若一份文档写为 `不纳入`，另一份写为当前核心范围，则判为 `冲突`
- 若一份文档写为 `待确认`，另一份默认当成已锁定，则判为 `待澄清`

### 4.6 来源仓库承接关系一致性

检查内容：

- `SleeperCloudQuant-old`
- `TradingAgents-CN-main`
- `rqalpha-master`
- `vnpy-master`
- `backtrader-master`

检查目标：

- 主承接来源、语义来源、参考来源角色前后一致
- 不出现来源角色越级漂移

判定规则：

- 若来源角色在各文档中一致，则判为 `一致`
- 若同一来源在某文档中是主拼接来源、在另一文档中却被当作冻结参考，则判为 `冲突`
- 若来源角色未冲突但表达不够稳定，则判为 `待统一表述`

## 五、检查输出格式

检查结果建议统一使用以下结构：

1. `已验证一致项`
2. `发现的冲突项`
3. `待统一表述项`
4. `待补齐边界项`
5. `建议修正优先级`

每个问题项建议至少包含：

- 所属维度
- 涉及文档
- 问题描述
- 影响范围
- 建议处理方式

## 六、冲突等级

### 6.1 P1 严重冲突

定义：

- 会导致模块边界错误
- 会导致对象语义互斥
- 会直接影响后续实现方向

示例：

- `BacktestResult` 在一份文档中被定义为标准化结果对象，在另一份文档中却被当作运行时原始包

### 6.2 P2 中等冲突

定义：

- 不立即阻塞规划，但会造成后续文档或实现返工

示例：

- `provider` 一词在一份文档中指外部数据来源，在另一份文档中又泛指任意外部服务来源

### 6.3 P3 轻微不一致

定义：

- 主要是术语、表述或状态粒度不统一
- 不影响当前方向，但建议统一

示例：

- 同一概念在不同文档中使用略不同命名

## 七、处理优先级

1. 先处理 `P1 严重冲突`
2. 再处理依赖方向相关的 `P2`
3. 最后统一 `P3` 术语与表述

## 八、当前不做的事

- 不直接修正文档内容
- 不新增实现约束
- 不进入第一批候选文件映射
- 不核对来源仓库源码实现

## 九、后续建议

1. 先按本计划执行一次实际一致性检查
2. 形成问题清单后，再决定是否批量修正文档
3. 文档一致性稳定后，再进入第一批候选文件映射清单

## 十、发布判断

### 已验证项

- 当前主干规划文档已足够进入系统性一致性检查阶段
- 检查维度可以覆盖术语、对象、职责、依赖、范围状态和来源角色

### 未验证项

- 实际是否存在冲突
- 冲突是否集中在少数文档还是广泛分布

### 阻塞原因

- 尚未执行正式的一致性检查

### 潜在风险

- 若跳过一致性检查直接进入文件级映射，后续会把文档冲突带入实现阶段

### 发布判断

- `已确认` 本文档可作为下一轮正式一致性检查的执行依据
- `待确认` 尚未产出实际冲突报告
