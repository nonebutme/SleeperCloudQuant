# web-app 首批页面清单与页面级非目标
时间：`2026-07-05`

## 一、文档定位

- `已确认`：本文档用于定义 `SleeperCloudQuant` 若进入 `web-app` 最小访问层时，首批页面清单、页面职责与页面级非目标。
- `已确认`：本文档是在 `web-app-minimal-access-layer-goals-and-boundaries.md` 基础上的进一步收束，只细化页面层，不直接触发实现。
- `已确认`：本文档继续沿用阶段 7 已形成的后端最小闭环，不新增前端专用后端扩面要求。

## 二、首批页面设计原则

首批页面清单应满足以下原则：

- 页面数量尽量少，但要能覆盖最小产品访问路径
- 每个页面只承接一类核心任务，不混入无关能力
- 优先复用当前已有 `market / factors / backtest / reporting` 访问面
- 页面展示以“能查、能提、能看”为先，不追求完整产品工作台体验

## 三、首批页面清单

### 3.1 页面 A：市场数据查询页

页面职责：

- 查询单标的价格历史
- 查询交易日历
- 查看最小同步状态

建议承接接口：

- `GET /api/market/price-history`
- `GET /api/market/trading-calendar`
- `GET /api/market/sync-status/{dataset}`
- 如有必要，可触发既有最小同步接口，但不扩其语义

页面级非目标：

- 不做多数据源切换体验
- 不做复杂图表分析工作台
- 不做批量标的对比界面
- 不做财务、行业、基础资料全量聚合页

### 3.2 页面 B：因子查询页

页面职责：

- 查看因子定义
- 查询股票池成员
- 查询单标的因子摘要
- 查询截面摘要、因子值与 top-n 排序结果

建议承接接口：

- `GET /api/factors/definitions`
- `GET /api/factors/pool-members`
- `GET /api/factors/summary`
- `GET /api/factors/cross-section-summary`
- `GET /api/factors/values`
- `GET /api/factors/top-n`

页面级非目标：

- 不做因子编辑器
- 不做因子批量导出中心
- 不做复杂研究工作流编排
- 不做新的因子计算任务入口

### 3.3 页面 C：单次回测提交与结果查看页

页面职责：

- 提交单次回测请求
- 查看单次回测最小返回结果
- 作为后续查看 run detail 的页面跳转入口

建议承接接口：

- `POST /api/backtest/run-once`
- `GET /api/reporting/run-detail/{run_id}`

页面级非目标：

- 不做批量实验工作台
- 不做异步任务中心
- 不做任务取消、重试、排队视图
- 不做高级策略编辑器

### 3.4 页面 D：reporting 只读结果页

页面职责：

- 查看单次回测 run detail
- 查看 batch summary
- 展示既有 reporting 冻结基线下的结果对象

建议承接接口：

- `GET /api/reporting/run-detail/{run_id}`
- `GET /api/reporting/batch-summary/{experiment_id}`

页面级非目标：

- 不做 reporting 列表页扩展
- 不做搜索、过滤、收藏或版本管理
- 不做导出中心
- 不做快照存储浏览入口

## 四、首批页面结构建议

### 4.1 导航结构建议

首批页面导航建议保持极简：

1. 市场
2. 因子
3. 回测
4. 报告

### 4.2 页面跳转关系建议

建议只保留以下最小跳转关系：

- 回测提交成功后，可跳转到对应 run detail
- batch summary 若已有既有结果，可从报告页直接查看
- 因子页与市场页默认彼此独立，不强行联动

### 4.3 当前不建议出现的页面

首批阶段不建议新增以下页面：

- 首页大盘总览
- AI 分析页
- 配置中心页
- 报告导出页
- 历史版本页
- 实验管理后台
- 用户/权限页

## 五、页面级共通非目标

以下事项应作为所有首批页面的共通非目标：

- 不做复杂卡片式运营化首页
- 不做前端专用聚合接口倒逼
- 不做页面层缓存与任务系统扩展
- 不做大而全的筛选器体系
- 不做移动端适配
- 不做登录、会话或权限流程

## 六、页面清单成功标准

若进入 `web-app` 首批实现，页面层更适合以以下标准判断是否达标：

1. 四类页面都能独立承接一类核心任务
2. 页面调用的仍是当前阶段 7 已有最小接口面
3. 页面没有为了显示便利而倒逼后端扩字段或扩 route
4. 页面之间跳转关系简单清晰
5. 首批页面能为后续是否继续扩 Web 层提供真实使用反馈

## 七、阶段判断

- `建议`：若继续推进 `web-app`，首批实现应只围绕本文档中的四类页面展开。
- `建议`：若后续有人试图把 AI、导出、配置中心或复杂实验管理一起带入，应视为越过首批边界，需要重新定义阶段范围。
- `已确认`：在页面清单与页面级非目标明确后，下一步才适合定义首批实现批次的具体任务范围。
