# 阶段 77.0｜治理基线对齐

## 1. 目标

在阶段 76.9 功能基础上，修复项目阶段、技术画像、数据模型、运行时、验证、角色和记忆记录的治理漂移，为“查看结果 / 查看分析”调整建立可审批入口。

本阶段不修改产品功能代码，不启动全市场长周期回测，不执行外部数据同步。

## 2. 已确认事实

- 最新完成功能阶段为 76.9。
- 项目已具备本地 A 股数据、因子、版本化策略、三模式回测、结果查看和专业报告能力。
- 实际技术栈为 Python 3.14、标准库 HTTP 服务、原生 Web 前端和本地 SQLite/JSON。
- 规范 A 股行情最新日期为 2026-07-17。
- 2026-07-25 统一验证在 A 股源质量门禁处中止，前四项验证通过。
- 过去三天角色记录和记忆闭环存在失真，不能继续把单一前端角色作为跨前后端交付的完整记录。

## 3. 本阶段交付

- 补全项目画像、技术边界、数据模型和运行时说明。

- 已建立正式项目记忆目录；两条 staging 候选已校验并同步至根级 staging，未提前晋升。

## 4. 角色链基线

阶段 77 的默认完整链路：

1. `orchestrator`：收敛范围、角色、风险和升级条件。
2. `product-planner`：定义结果/分析目标、信息层级和验收标准。
3. `business-analyst`：审核三模式账户、样本、指标和金融表达。
4. `ui-designer`：提供可审批的结果/分析 MVP。
5. `solution-architect`：冻结数据契约、加载边界和兼容策略。
6. `frontend-dev` / `backend-dev`：按触点分别实现。
7. `qa-lead`：工具验证、浏览器路径与模式隔离。
8. `quality-evaluator`：给出交付判断。
9. `memory-curator`：同步阶段文档、日志和可复用经验。

局部修复可走快速流，但日志必须说明跳过角色、验证范围和退出快速流条件。

## 5. 阶段 77.1 人工确认问题

用户需要重点确认：

1. “查看结果”默认首先看到哪些事实与图表。
2. “查看分析”默认首先看到哪些结论、证据和风险。
3. 单股、独立账户批量回测、投资组合回测三个模式的首屏差异。
4. 是否保留统一查看器外壳、同模式任务快捷切换和固定抽屉。
5. 独立账户批量回测是否坚持任务级结果优先、单股诊断按需选择。
6. 结果/分析的返回路径、URL 状态和空/失败状态。

## 6. 验收结果

### 已验证项

- 治理文档已从模板/待确认状态对齐到阶段 77 实际系统。
- 技术栈、数据库表和运行入口来自当前代码与 SQLite 只读检查。
- 验证基线已明确局部回归与全系统发布门禁的区别。
- 阶段 77.1 的人工审批入口已形成。

### 未验证项

- 行情恢复后的完整正式验证。
- 用户对结果/分析 MVP 的业务与交互确认。
- 全市场真实长周期任务。

### 阻塞原因

- A 股行情新鲜度质量门禁未恢复。
- 阶段 77.1 产品与业务口径尚待用户确认。

### 潜在风险

- 当前结果与分析共享预加载链路，可能造成性能浪费和语义混淆。
- 独立账户批量回测默认加载第一只建仓股票，可能让用户误判为任务整体结果。
- 历史日志格式损坏会降低角色与记忆统计可信度。
- 根级 logger 的内置角色清单落后于正式角色注册表，当前尚不识别 `verification-baseline-runner`；跨项目脚本修复需单独授权。

### 发布判断

- 阶段 77.0 治理基线可交付。
- 可进入阶段 77.1 人工需求与交互确认。
- 当前仍不可宣称全系统可发布。
