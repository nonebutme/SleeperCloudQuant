# 拂经 v2 V7 阶段 0—1 语义冻结与数据正确性门禁验收

日期：2026-08-21

## 1. 本轮范围

本轮只完成阶段 0 与阶段 1 的机制建设和隔离验证：

- 冻结 V7 研究语义、开发区间与样本外边界；
- 把量比确定为第六个受治理候选因子，但尚未实现计算器或生成制品；
- 强制严格策略声明的复权口径必须与实际运行口径一致；
- 对交易状态空值、停牌状态与正成交量冲突实施失败关闭；
- 将交易状态语义检查接入 M3 快速质量检查。

本轮没有修改正式行情数据库，没有运行全 A 因子计算，没有读取或打开封存样本外数据。

## 2. 已确认语义

1. V7 行情运行口径固定为 `qfq`，声明与实际运行不一致时拒绝执行。
2. 量比采用“当日成交量 / 前 5 个交易日平均成交量（不含当日）”，作为第六个受治理候选因子；在实现和验证前，不把现有策略内代理固化为正式因子。
3. 开发研究区间为 `2015-01-05..2024-12-31`；候选样本外从 `2025-01-01` 开始，继续封存且本轮不访问。
4. 旧数据版本与旧因子制品只作为历史开发证据；阶段 1 数据修复后发布的后继版本才可申请成为 V7 全 A 研究基线。

详细决策见 `docs/decision-log/fujing-v2-v7-semantic-decisions.md`。

## 3. 已实现门禁

### 3.1 策略研究与运行门禁

- 严格 `DATASET_CONTRACTS` 声明 `a_share_daily.adjustment` 后，回测、独立选股和共享组合入口均校验实际口径。
- 点时数据覆盖校验同时覆盖 `same_trade_date` 与 `as_of_trade_date`。
- `trading_status.is_tradable` 缺失或为空时失败关闭。
- `is_tradable=false` 且对应行情 `volume>0` 时失败关闭。

### 3.2 M3 快速质量门禁

新增 `trading_status_semantics` 规则，并加入 M3 默认规则集：

- `unknown_tradability`：交易状态已存在，但 `is_tradable` 为空；
- `suspended_with_positive_volume`：状态不可交易，但所选行情口径存在正成交量。

异常以阻断级质量问题写入治理台账；普通用户可在 M3 查看证据并作受审计处置。交易状态专用自动修复任务尚未产品化，当前不得把“发现异常”等同于“已修复”。

## 7. 交易状态修复闭环补充（2026-08-21）

### 7.1 根因确认

正式库只读分组确认：

- 194,678 条 `is_tradable IS NULL` 全部来自 `stage78.3:evidence_gap`；
- 当前证券中有 193,641 条空值，其中 193,631 条同日存在正成交量，10 条只有零成交量行情；
- 1,937 个“不可交易但正成交量”证券日全部来自 `akshare:stock_tfp_em:eastmoney`；
- 现有停牌适配曾把上游返回记录统一归一到查询目标日，没有先核对原始 `停牌时间`、`停牌截止时间` 和 `预计复牌时间`；
- 按原始区间重新分类后，902 条可确认目标日不在上游停牌区间内，1,035 条仍属于明确停牌来源与正成交量冲突，必须保留人工证据裁决。

### 7.2 新增数据防错

停牌适配现在只在目标日确实位于原始停牌区间时生成该日不可交易事实：

- 目标日早于停牌开始日：忽略；
- 目标日晚于停牌截止日：忽略；
- 目标日等于或晚于预计复牌日：忽略；
- 原始停牌开始日缺失：不制造日级停牌事实。

### 7.3 M3 确定性修复

新增交易状态专用的两步 API 和页面入口：

1. 预览只读当前状态、原始上游区间和规范行情证据，`writes=0`；
2. 仅以下情形允许写入 `status=normal, is_tradable=true`：
   - 未知可交易性且同日存在正成交量；
   - 历史缺口停牌推断被后续正成交量推翻；
   - 上游原始停牌区间明确不包含该交易日，且同日存在正成交量。

明确停牌区间仍包含目标日、但行情存在正成交量时，系统返回 `manual_evidence_required`，不发放执行令牌、不改写事实。每次执行令牌限一个问题、15 分钟、一次使用；执行后进入 `awaiting_recheck`，旧状态事实封装在新证据中，并要求用户回到来源质量扫描执行复查。

通用“行情重拉”入口现在拒绝交易状态语义问题，避免生成不能修复交易状态的伪任务。M3 批量重拉按钮对该规则禁用。

### 9.7 交易状态快速复检与独立修正版闭环（仅实现，2026-08-24 至 2026-08-25）

本节冻结交易状态物理修复完成后的快速复检与独立修正版发布契约。源码实现与隔离专项已经完成，但不代表已对正式数据库执行复检或发布。

独立修正版采用“基准版本之后的全部未发布运行”聚合语义，而不是选择某一个运行单独发布：

- 发布预览必须显式冻结基准数据版本及其 manifest 哈希，并聚合该基准之后所有已完成、尚未归属数据版本的交易状态修复运行；
- 聚合运行集合、各运行 checkpoint/候选清单哈希、change-set 哈希、写入键摘要、操作人和授权依据共同进入不可变发布证据；
- 同一修复运行不得被两个修正版重复消费；基准之后存在遗漏、未完成、失败、暂停或证据漂移的运行时 fail-closed；
- 运行消费关系由追加式 `trading_status_remediation_release_bindings` 独立保存，不能只依赖当前父版本的成员详情；因此后续普通增量版本即使重建交易状态成员，也不会让已消费运行或旧封口任务重新进入待发布集合；
- 快速复检固定使用 `all_symbols`，覆盖当前及历史证券。发布前重新预演得到的自动候选和人工候选都必须为 0；人工项不能通过忽略、缩小为 `current_symbols` 或仅标记“待处理”绕过，必须先完成可审计裁决或事实修复。

发布制品必须建立真实物理状态与治理证据的绑定：

- `security_trading_status_daily` 成员使用规范字段、稳定排序和明确算法计算真实物理内容哈希，不以行数、证券数、日期范围或拼接字符串代替内容哈希；
- 发布质量报告冻结快速复检结果、聚合运行集合、change-set 哈希、物理内容哈希、基准版本、基准 manifest 哈希和生成规则版本；
- 发布预览冻结上述输入并生成预览哈希；正式发布必须在同一数据库事务内重新核对，任何物理漂移、运行集合变化、报告变化或基准变化都会拒绝发布；
- 新版本从显式基准版本继承成员，只替换 `security_trading_status_daily` 成员；其他数据集及复权口径成员必须与基准版本逐项一致，不借交易状态修正版夹带行情、日历、指数、生命周期、公司行动、复权因子或证券目录变化。

独立发布使用专用的父版本 CAS 与幂等契约：

- 请求必须携带基准版本号、基准 manifest 哈希、聚合发布预览哈希和精确确认信息；只有当前父版本状态仍与预览一致时才能提交；
- 快速复检先生成不可变质量报告；专用发布事务必须重新核对报告 ID、`passed` 状态和 payload 哈希。版本、成员、全部运行消费绑定和旧 `published` 状态切换必须在同一事务内完成，不能先发布版本、再在第二个事务中补运行归属；
- 相同基准、运行集合、change-set、报告和物理哈希的重复请求只能返回同一版本；任一冻结输入不同则视为冲突，不能把较旧修正版重新提升为最新发布；
- 发布成功只生成新的已发布修正版，不自动修改 `default_data_version_id`。默认研究版本仍由 M5 人工确认后单独切换，历史 Run 的显式版本绑定保持不变。

当前版本机制仍有明确边界：版本成员冻结的是 manifest，不是完整物理快照；交易状态修复已对共享物理表进行原位更新，旧版本消费者目前也没有完整的按版本交易状态修正层。因此，新修正版可以受治理地声明当前物理状态，但不能据此声称旧版本已经恢复严格物理隔离或能够精确重放修复前的交易状态。后续仍需追加式修正记录、版本化覆盖层或等价的差异快照，并让所有交易状态消费者按显式版本解析；在此之前，发现旧成员哈希与当前物理状态不一致时应失败关闭，不应静默读取当前事实冒充旧版本。
